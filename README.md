# CloudVault

> Personal cloud storage with secure file lifecycle management, realtime state, resumable large-object architecture, and owner-scoped intelligent retrieval.

## Production deployment

**Vercel:** https://cloudvault-distributed-cloud-storag-srivastavaadityamohan0-6847.vercel.app

CloudVault is built around one security rule:

**A signed-in user can discover and access only content they own, unless a specific file has been deliberately exposed through a temporary share link.**

The repository has two intentional runtime profiles:

- a **hosted product profile** using Vercel + Supabase, with Backblaze B2 support for large objects when configured
- a **local distributed-systems profile** using FastAPI, PostgreSQL, MinIO, RabbitMQ, Celery, Redis, Elasticsearch, Prometheus, and Grafana

No benchmark, scale, retrieval-quality, or large-upload claim is presented as measured until it has actually been tested.

## Upload policy

CloudVault separates the **product upload ceiling** from the **active storage-provider ceiling**.

Current product configuration:

- product maximum: **1.5 GiB per file**
- Supabase direct-upload ceiling: **50 MB**
- large-file provider: **Backblaze B2**
- B2 multipart part size: **16 MiB**
- default multipart parallelism: **3**
- B2 feature flag: disabled until real credentials and CORS are configured

This means the architecture and UI support the 1.5 GiB policy, but the hosted deployment must not claim that a real 1.5 GiB transfer is production-verified until R2 is connected and the end-to-end checklist in `docs/B2_SETUP.md` passes.

Large storage capacity is also independent from AI extraction capacity. Uploading a large video or binary object does not imply that the full object is embedded or sent to a generative model.

## Privacy model

Privacy is enforced below React.

### Database isolation

RLS scopes these resources to `auth.uid()`:

- files
- folders
- file versions
- embedding chunks
- multipart-upload sessions
- activity events
- AI query telemetry
- user AI preferences
- share-link management records

### Storage isolation

Supabase Storage object paths begin with the authenticated user ID, and policies verify that owner path before select, insert, update, or delete.

B2 credentials never belong in browser code. Large-object operations use signed part/object URLs generated by authenticated server-side Edge Functions.

### Folder lifecycle

Deleting a folder is not a raw database delete.

CloudVault:

1. recursively identifies active descendants
2. soft-deletes active files in that folder tree
3. marks the folder tree as one trash group
4. detaches the trash root from its former parent
5. exposes the folder as one recoverable item in Trash
6. restores the group under its previous parent when that parent still exists
7. permanently removes provider objects and version history only through the provider-aware purge function

Individually deleted files are kept separate from files that were trashed as part of a folder group.

### Semantic retrieval isolation

Hybrid search filters both relational file metadata and vector chunks to the current authenticated owner.

The retrieval layer combines:

- Supabase `gte-small` embeddings
- pgvector cosine similarity
- PostgreSQL full-text search
- configurable semantic/lexical weighting

### Public sharing

A user must deliberately create a link for a specific file.

- raw share tokens are not stored
- only SHA-256 token hashes persist
- link consumption is atomic
- links can expire
- links can enforce a maximum use count
- links can be revoked
- downloads resolve to short-lived signed object URLs
- Supabase and B2 objects use the same public sharing model

### Optional grounded generation

The configured provider is Gemini, currently `gemini-3.8-flash`.

Private evidence is sent to Gemini only when all three conditions are true:

1. deployment setting `generative_ai_enabled=true`
2. a server-side `GEMINI_API_KEY` exists
3. the signed-in user explicitly enables `allow_external_ai`

Without all three, CloudVault stops after private retrieval and returns evidence without inventing a generated answer.

## Security decisions

- private Storage bucket
- owner-based RLS
- owner filtering inside retrieval
- signed downloads
- hashed share tokens
- atomic share consumption
- security-invoker folder/file lifecycle RPCs
- authenticated-only folder trash/restore RPC execution
- provider-aware permanent purge
- server-side B2 credentials
- explicit external-AI consent
- secrets outside Git
- publishable Supabase key only in the browser
- service-role credentials restricted to trusted Edge Functions where genuinely required

The historical `index-chunks` Edge Function URL is intentionally kept as an authenticated **410 Gone** compatibility stub. `index-file` is the supported indexing path.

## Current external configuration gates

The code is complete for these paths, but the hosted deployment still needs provider-side configuration before they can be truthfully called active:

- **Backblaze B2**: bucket, scoped credentials, production CORS, then `r2_enabled=true`
- **Passkeys**: Supabase project WebAuthn/passkey configuration for the final production domain
- **Gemini generation**: server-side API key + deployment enablement + per-user consent
- **Supabase leaked-password protection**: Pro-plan-only control; unavailable while CloudVault keeps the free-only hosting constraint. The web UI enforces a stronger 12+ character mixed-password policy for new registrations and resets as a separate mitigation.
- **Supabase Auth redirect allowlist**: final production reset-password domain

## Storage-provider compatibility

Backblaze B2 is the primary large-object target. The Edge Functions retain legacy Cloudflare R2 support for existing deployments, but new CloudVault deployments should use B2 unless a different S3-compatible provider is intentionally configured.

## Cost policy

CloudVault remains free-first.

The hosted architecture is designed to function on free tiers and open-source components. Provider quotas and terms can change, so the system should stop or degrade gracefully when a free quota is exhausted rather than silently upgrading itself to a paid plan.
