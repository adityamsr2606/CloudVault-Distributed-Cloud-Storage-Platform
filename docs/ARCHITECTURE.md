# CloudVault Architecture

## Design goals

CloudVault is organized around a few practical constraints:

1. Object bytes and relational metadata have different storage characteristics.
2. AI processing must not block normal storage operations.
3. Search must preserve the same tenant boundary as the primary database.
4. Infrastructure should remain understandable enough to run locally.
5. Components are introduced only when they solve a concrete problem.

## Component responsibilities

### FastAPI

Owns synchronous HTTP concerns: authentication, validation, metadata transactions, quota checks, and task publication.

### PostgreSQL

Stores authoritative application metadata. A search index is never treated as the source of truth for file ownership or lifecycle state.

### MinIO

Stores file bytes using an S3-compatible interface. Object keys are generated by the server and include the user and file identifiers.

### RabbitMQ and Celery

Decouple storage availability from CPU/model-heavy indexing. Tasks use late acknowledgement and bounded retries.

### Elasticsearch

Stores lexical content and dense vectors for hybrid retrieval. Indexed chunks carry owner identifiers and are filtered during retrieval.

### Redis

Currently serves as the Celery result backend and is reserved for later rate-limit/cache work where measured benefit justifies it.

### Prometheus and Grafana

Expose and visualize API and AI subsystem behaviour.

## Consistency model

CloudVault writes the object before committing file metadata. If the relational transaction fails, the API attempts compensating object deletion.

AI indexing is eventually consistent. A newly uploaded file moves through:

```text
uploaded -> indexing -> ready
                    \-> failed
```

The file remains stored even if search indexing fails.

## Why this is not split into many microservices

The initial implementation is a modular monolith plus background workers. Splitting authentication, metadata, search orchestration, and storage orchestration into separately deployed services would add network failure modes and deployment overhead before independent scaling is justified.

Elasticsearch, PostgreSQL, MinIO, RabbitMQ, Redis, and the worker already provide independently scalable infrastructure boundaries where they are useful.

## Failure boundaries

- PostgreSQL unavailable: metadata operations fail closed.
- MinIO unavailable: upload/download fails without pretending success.
- RabbitMQ unavailable: task publication fails and should become an operational alert.
- Elasticsearch unavailable: file storage remains available; search/indexing degrades.
- embedding model failure: worker retries and records failed indexing state.

Future work should add a transactional outbox for task publication if stronger delivery guarantees become necessary.
